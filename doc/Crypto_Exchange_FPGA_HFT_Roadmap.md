# 面向 Crypto 交易所的 FPGA 低时延交易系统复现路线图

## 一、文档目的

基于论文《An FPGA-Based High-Frequency Trading System for 10 Gigabit Ethernet with a Latency of 433 ns》的架构思想，回答下面三个问题：

1. 能否针对一个特定的 crypto 交易所实现类似系统。
2. 如果能，应该拆成哪些可实现的 FPGA 模块。
3. 从 0 到 1 的工程复现路线图应如何设计。

本文采用一个具体目标来讨论：

- 目标交易所：Binance USD-M 永续合约
- 目标品种：先从单一高流动性品种开始，例如 BTCUSDT
- 目标风格：先做单品种、单策略、单账户、确定性低时延链路

之所以选择这一设定，是因为它与原论文一样，适合先做高度专用化系统，再逐步扩展为多品种、多策略平台。

---

## 二、先给结论

**可以做出“类似”的 FPGA 系统，但不能机械照搬论文中的 433 ns 结论。**

更准确地说：

1. 如果“类似”指的是架构思想，即把市场数据接收、协议解析、订单簿维护、策略判断、下单编码这条热路径尽量压进 FPGA，那么答案是可以。
2. 如果“类似”指的是对单一交易所、单一品种、有限深度订单簿、固定风控和固定策略做专用化硬件实现，那么答案也是可以。
3. 如果“类似”指的是在真实公网 crypto 交易所环境下复现论文的 433 ns 端到端时延，那么答案通常不可以。

核心原因不在 FPGA，而在交易所接口形态：

1. crypto 交易所通常不是交易所机房内的专用裸 TCP/UDP 低时延接口场景。
2. 常见接口往往包含 TLS、WebSocket、JSON 或更复杂的会话层。
3. 公网链路抖动、交易所限频、账户风控、撮合侧排队延迟，都会远大于 FPGA 内部 100 ns 到 1000 ns 量级的计算延迟。

因此，合理目标不是“复刻论文数字”，而是：

**复刻论文的方法论，把可控的内部热路径做成亚微秒到低微秒级，并把不可控的外部链路延迟降到系统允许的最低。**

---

## 三、为什么 crypto 交易所场景与论文不同

原论文成立的关键前提，是它针对台湾期货市场做了极强的专用化：

1. 协议是定制且稳定的。
2. 网络层只实现必要的 ARP、UDP、TCP。
3. 订单簿是单产品、前五档、片上存储。
4. 交易逻辑很简单，是固定套利逻辑。
5. CPU 和 PCIe 被尽量移出热路径。

而面向 Binance 这类 crypto 交易所，系统差异主要来自以下几点。

### 3.1 接口层通常更重

许多 crypto 接口并不是“裸市场数据 + 裸下单协议”，而是：

1. 市场数据通过 WebSocket 推送。
2. 下单通过 WebSocket API、REST 或机构接口。
3. 连接层常常包含 TLS。
4. 应用层常常包含文本字段、变长字段、签名、时间戳和限频规则。

这会显著增加报文解析、会话管理和安全处理复杂度。

### 3.2 外部网络不可控

论文中的 433 ns 仅覆盖 FPGA 内部的数据通路，不覆盖公网往返。而 crypto 交易的主要延迟瓶颈往往是：

1. Internet 或跨运营商网络时延。
2. 交易所接入网关排队。
3. 对端风控与撮合队列。
4. API rate limit 和会话节流。

### 3.3 协议与业务规则变化更频繁

crypto 交易所的字段、限速、签名方式、断线重连语义、订阅方式都比传统专用交易接口更容易变化，因此系统必须把“协议适配层”和“核心交易热路径”解耦。

## 四、适合复现的目标形态

如果要把论文迁移到 Binance USD-M 永续合约，最合理的复现目标不是“全栈都进 FPGA”，而是下面两级方案。

### 4.1 方案 A：激进型全硬件热路径

目标：尽可能让 FPGA 直接看到市场数据并直接产出订单报文。

特征：

1. 网卡侧直接接入 10/25GbE。
2. 在 FPGA 中做 TCP 会话管理。
3. 如接口要求 TLS，则在 FPGA 中加入 TLS 终止或在前置设备中卸载 TLS。
4. 在 FPGA 中做 WebSocket 帧解析或专有二进制协议解析。
5. 在 FPGA 中完成订单簿、策略、风控、下单编码。

优点是热路径最短。

缺点是实现复杂度极高，且一旦交易所协议变化，重构成本大。

### 4.2 方案 B：务实型分层架构

目标：保留论文的核心思想，但把不稳定、复杂、经常变化的会话与安全层放在主机侧。

特征：

1. Host 负责 TLS、WebSocket、鉴权、签名、心跳、重连。
2. Host 把市场数据规范化成固定长度内部二进制消息，再通过 PCIe 或共享内存送入 FPGA。
3. FPGA 负责订单簿、衍生特征、策略判断、风控快路径、订单意图生成。
4. Host 把 FPGA 输出的订单意图转换为真实交易所 API 请求。

这是更建议的首版方案，因为它能先把最有价值、最稳定、最适合硬件化的部分做出来。

如果后续拿到交易所更低时延的机构接口，再逐步把 Host 的功能往 FPGA 迁移。

## 五、面向 Binance USD-M 的 FPGA 模块清单

下面给出一个从论文映射出来、且适合工程落地的模块划分。为了可维护性，建议分为三层：外部接入层、硬件热路径层、控制与运维层。

### 5.1 外部接入层

这一层决定系统如何接上真实交易所。

#### 模块 1：物理网络接口模块

职责：

1. 提供 10/25GbE 物理接入。
2. 完成 MAC、PCS/PMA 对接。
3. 提供时间戳与报文捕获能力。

实现建议：

1. 如果用 SmartNIC 或 FPGA 板卡，优先使用成熟以太网 MAC/PCS IP。
2. 所有 ingress/egress 报文都打时间戳，便于后续 wire-to-wire 剖析。

#### 模块 2：会话卸载模块

职责：

1. 管理 TCP 连接。
2. 视接口要求决定是否处理 TLS。
3. 负责心跳、断线重连、序列号与会话状态。

实现建议：

1. 首版放在 Host。
2. 如果后续确定可使用稳定的专用机构接口，再把 TCP/TLS 的一部分迁到 FPGA。

#### 模块 3：交易所协议适配模块

职责：

1. 解析市场数据消息。
2. 解析成交、撤单、拒单、账户状态回报。
3. 将交易所原生消息转换为内部统一消息格式。

内部建议定义固定长度消息，例如：

- `MD_SNAPSHOT`
- `MD_INCREMENTAL`
- `TRADE_TICK`
- `ORDER_ACK`
- `FILL`
- `RISK_EVENT`

这层是系统中最应该与核心策略解耦的部分。

### 5.2 硬件热路径层

这一层对应论文真正的价值所在。

#### 模块 4：市场数据标准化输入模块

职责：

1. 把 Host 或网口送来的消息统一成定长流接口。
2. 给每条消息附加接收时间戳、序列号和品种 ID。
3. 对异常消息做快速过滤。

输出接口建议固定化，避免后续模块处理变长消息。

#### 模块 5：单品种低时延订单簿模块

职责：

1. 维护目标品种的买一到买 N、卖一到卖 N。
2. 支持增量更新、快照校正、序列一致性检查。
3. 维护派生字段，例如 mid-price、spread、microprice、imbalance。

设计建议：

1. 首版不要做全深度通用订单簿。
2. 先做单品种、固定深度，例如前 8 档或前 16 档。
3. 全部放片上 BRAM 或 URAM，避免外部 DRAM 进入热路径。
4. 多品种扩展时，优先采用“多实例并行”，不要一开始就设计复杂共享架构。

这一步与论文中的单产品 order book 完全同构，是最值得复现的部分。

#### 模块 6：特征计算模块

职责：

1. 基于订单簿计算策略所需的低维特征。
2. 对每个市场事件增量更新特征。
3. 输出给策略引擎使用。

可选特征包括：

1. best bid、best ask、spread
2. microprice
3. order book imbalance
4. top-k depth ratio
5. short-window event count
6. short-window trade imbalance

这一步的重点是只保留真正影响决策的特征，不要把完整数据科学流水塞进 FPGA。

#### 模块 7：策略引擎模块

职责：

1. 根据特征和持仓状态产生买卖意图。
2. 支持确定性、固定流水级数的策略判断。
3. 输出限价单、撤单、改单或不动作。

首版建议策略：

1. 单品种被动做市
2. 极简价差捕捉
3. 基于订单簿失衡的方向性短线策略

不建议首版就做：

1. 需要大量浮点运算的复杂模型
2. 跨市场统计套利
3. 依赖大窗口历史状态的深模型

如果需要模型化，可以先用离线训练，再把推理压缩成定点阈值树、线性打分或小型查表模型。

#### 模块 8：快路径风控模块

职责：

1. 检查最大持仓。
2. 检查单笔最大下单量。
3. 检查最小价差、最大偏离。
4. 检查节流与冷却时间。
5. 在异常情况下快速熔断。

这一层不能只放在 Host，因为只要它进入热路径，就会抵消 FPGA 的价值。

#### 模块 9：订单意图生成模块

职责：

1. 将策略输出转换为统一内部订单对象。
2. 生成 `NEW`、`CANCEL`、`REPLACE` 等动作。
3. 附带 client order id、价格、数量、方向、时序标签。

建议采用固定长度订单描述结构，便于 Host 或 FPGA 网络模块继续处理。

#### 模块 10：订单发送队列模块

职责：

1. 存储待发订单。
2. 根据交易所限频和会话状态调度发送。
3. 在撤单和新单冲突时按本地规则排序。

这一块类似论文中的 order FIFO，但在 crypto 场景下要额外考虑 rate limit 和重发语义。

### 5.3 控制与运维层

#### 模块 11：Host 控制平面模块

职责：

1. 配置策略参数。
2. 管理会话、鉴权、签名和重连。
3. 记录日志、风控事件、订单结果。
4. 提供回放、回测、在线监控接口。

#### 模块 12：时钟同步与测量模块

职责：

1. 提供全链路时间戳。
2. 衡量 market-data ingress 到 order-intent egress 的内部时延。
3. 衡量 Host 规范化前后、API 发出前后的边界时延。

没有这一层，就无法证明 FPGA 是否真的带来收益。

#### 模块 13：回放与验证模块

职责：

1. 回放历史 market data。
2. 将 FPGA 输出与软件金标准逐条比对。
3. 验证丢包、乱序、重连、快照恢复等异常流程。

这一步在 crypto 场景尤其重要，因为真实接口变化频繁，且调试窗口短。

## 六、哪些模块必须在 FPGA，哪些可以先留在 Host

建议优先级如下。

### 6.1 必须进入 FPGA 的模块

1. 市场数据标准化输入后的解析通路
2. 单品种订单簿
3. 派生特征计算
4. 策略引擎
5. 快路径风控
6. 订单意图生成
7. 发送队列和节流快路径

这些模块稳定、确定、规则清晰，最适合做成低时延硬件流水。

### 6.2 首版建议保留在 Host 的模块

1. TLS
2. WebSocket 会话
3. API 鉴权与签名
4. 断线重连与订阅恢复
5. 订单结果持久化与审计

原因很简单：这些功能会频繁变动，而且即便放进 FPGA，也未必成为主要收益来源。

### 6.3 当你们拿到更底层接口后再考虑迁移的模块

1. TCP offload
2. TLS offload
3. WebSocket 帧处理
4. 原生交易所订单编码

这部分只有在接口长期稳定、且你们确信会话层已成为瓶颈时才值得做。

## 七、从 0 到 1 的复现路线图

下面给出推荐的阶段式推进方式。每一阶段都必须有可量化交付物，否则很容易在“低延时系统”里陷入概念开发。

### 阶段 0：范围收敛

目标：把问题压缩到可做。

必须先确定：

1. 只做一个交易所。
2. 只做一个账户。
3. 只做一个品种。
4. 只做一个策略。
5. 只做一种下单动作组合。

建议输出：

1. 接口白名单
2. 策略输入字段白名单
3. 风控规则白名单
4. 时延预算表

退出条件：系统边界文档冻结。

### 阶段 1：软件金标准系统

目标：先有一个完全正确的软件版参考实现。

内容：

1. 接入真实或录制的 Binance 市场数据。
2. 在软件中实现标准化消息总线。
3. 在软件中实现单品种固定深度订单簿。
4. 在软件中实现策略与快路径风控。
5. 在软件中实现订单意图到真实 API 请求的映射。

退出条件：

1. 历史回放结果稳定。
2. 订单簿与交易所参考结果一致。
3. 策略输出可重现。

### 阶段 2：离线数据采集与回放框架

目标：建立一个不依赖真实在线连接也能迭代硬件的验证环境。

内容：

1. 录制原始 market data。
2. 录制订单回报与成交回报。
3. 生成内部标准化二进制事件流。
4. 建立纳秒或微秒级时间戳回放机制。

退出条件：可以在离线条件下完整重演一段交易日行情。

### 阶段 3：硬件平台选型与基线联调

目标：把板卡、主机、PCIe、时钟测量体系打通。

建议最低能力：

1. 支持 10/25GbE
2. 支持 PCIe Gen3/Gen4 x8 或以上
3. 片上 BRAM/URAM 足够容纳目标订单簿和特征状态
4. 有稳定的 DMA 通道

退出条件：

1. Host 到 FPGA 的固定长度消息链路跑通。
2. FPGA 到 Host 的订单意图回传跑通。
3. 基础时间戳有效。

### 阶段 4：FPGA 订单簿内核

目标：先把最稳定、收益最大的模块硬件化。

内容：

1. 定长事件输入接口
2. 固定深度订单簿更新逻辑
3. 序列号检查与异常标记
4. 快照重同步入口
5. 派生字段计算

退出条件：

1. FPGA 输出与软件订单簿逐条一致。
2. 在目标频率下 timing closure 完成。

### 阶段 5：FPGA 策略与快路径风控

目标：让系统能从行情事件直接得出订单动作。

内容：

1. 策略阈值与参数寄存器化
2. 持仓与挂单状态缓存
3. 下单、撤单、改单判定
4. 持仓上限、节流、冷却、价格保护

退出条件：

1. 软件与 FPGA 的策略判定在回放下逐条对齐。
2. 风控拒绝路径正确。

### 阶段 6：订单意图到交易所接口适配

目标：把 FPGA 输出变成真实可发送订单。

首版建议做法：

1. FPGA 只输出内部订单对象。
2. Host 负责签名、序列、会话和真实 API 调用。
3. 所有 ACK、reject、fill 再转回内部统一回报格式。

退出条件：能在测试环境或小规模真实环境完成下单闭环。

### 阶段 7：全链路性能测量

目标：回答“FPGA 到底带来多少收益”。

至少测量下列指标：

1. 标准化行情进入 FPGA 到订单意图输出延迟
2. Host 接收交易所消息到标准化消息生成延迟
3. Host 收到 FPGA 订单意图到真实 API 发送延迟
4. ACK 返回延迟
5. 各模块尾延迟和抖动

退出条件：形成正式 latency budget 表。

### 阶段 8：异常场景与生产化加固

目标：确保系统不是只在理想行情下工作。

必须覆盖：

1. 丢包
2. 乱序
3. 增量流中断
4. 快照与增量重建
5. 会话断开重连
6. 风控熔断
7. 交易所拒单
8. 本地状态与交易所状态不一致

退出条件：异常恢复流程全部经回放验证通过。

### 阶段 9：逐步扩大范围

顺序建议如下：

1. 单品种到少量品种
2. 单策略到多策略
3. 单账户到多账户
4. Host 协议适配到部分硬件卸载

每次只扩大一维，不要同时增加品种、策略和协议复杂度。

## 八、建议的内部消息格式

为了把协议变动和策略内核解耦，建议定义交易所无关的内部消息。

### 8.1 市场数据消息

固定字段建议：

1. `msg_type`
2. `symbol_id`
3. `exchange_ts`
4. `recv_ts`
5. `seq_no`
6. `side`
7. `price`
8. `qty`
9. `level`
10. `flags`

### 8.2 订单意图消息

固定字段建议：

1. `action`
2. `symbol_id`
3. `side`
4. `price`
5. `qty`
6. `time_in_force`
7. `strategy_id`
8. `risk_tag`
9. `local_order_id`
10. `emit_ts`

### 8.3 回报消息

固定字段建议：

1. `event_type`
2. `local_order_id`
3. `exchange_order_id`
4. `status`
5. `filled_qty`
6. `remaining_qty`
7. `price`
8. `reason_code`
9. `exchange_ts`
10. `recv_ts`

只要内部格式稳定，就可以把“换交易所”收敛成“重写协议适配层”，而不必推倒订单簿和策略硬件。

## 九、性能目标应该怎么定

建议把目标拆成三类，而不是只盯着一个总数字。

### 9.1 内部热路径目标

这是最接近论文的指标。

建议目标：

1. 标准化市场事件进入 FPGA 到订单意图输出，小于 1 µs
2. 单模块抖动尽量固定，尾延迟可控

### 9.2 边界接口目标

这是 crypto 场景下更真实的指标。

建议目标：

1. Host 原始消息到 FPGA 入口，小于 5 µs 到 20 µs
2. FPGA 输出到 Host 发单调用，小于 5 µs 到 20 µs

### 9.3 真实交易闭环目标

建议关注：

1. 下单 ACK 中位数
2. 下单 ACK P99
3. 撤单 ACK 中位数
4. 撤单 ACK P99
5. 从行情触发到订单被交易所确认的全链路分布

在 crypto 场景中，真正有业务意义的是分布而不是单次最小值。

---

## 十、主要技术风险

### 10.1 最大风险不是 FPGA 开发，而是接口现实

如果最终只能使用公网 WebSocket 和高层 API，那么外部链路会吞噬大量低延时收益。

### 10.2 订单簿正确性风险

crypto 增量行情常见问题是：

1. 快照与增量序列衔接复杂
2. 乱序或缺失导致本地簿漂移
3. 交易所升级后语义变化

如果订单簿重建不稳，后面的策略再快也没有意义。

### 10.3 风控和状态同步风险

本地认为的持仓、挂单、成交状态，必须与交易所状态持续校对，否则快路径会在高波动时触发错误动作。

### 10.4 可维护性风险

如果首版就把会话、TLS、协议、策略全部硬编码进 FPGA，后期维护成本会非常高。

---

## 十一、建议的首版实现范围

为了真正从 0 到 1 做出来，建议首版只做下面这些内容：

1. 单交易所：Binance USD-M
2. 单品种：BTCUSDT
3. 单账户
4. 单策略：固定阈值的订单簿失衡做市或超短线方向策略
5. 单机部署：Host + FPGA 板卡
6. Host 负责 TLS、鉴权、WebSocket/REST 或等效接口
7. FPGA 负责订单簿、特征、策略、快路径风控、订单意图生成

这一版做完后，已经足以回答两个最重要的问题：

1. 你们的策略热路径是否适合硬件化。
2. 在该交易所接口现实下，FPGA 的收益是否足以覆盖系统复杂度。

---

## 十二、最终判断

**可以针对一个特定的 crypto 交易所实现类似论文的 FPGA 系统。**

但“类似”的正确理解应当是：

1. 复用论文的专用化方法。
2. 把订单簿、特征、策略、快路径风控和订单生成压进 FPGA。
3. 把不稳定、复杂、变化快的协议与安全层留在 Host，至少在首版如此。

如果你们的目标是“在 Binance 这类交易所上做真实可运行系统”，这是一条现实路线。

如果你们的目标是“在公网 crypto 交易所上复刻 433 ns 端到端”，那就不是 FPGA 模块设计问题，而是场景假设本身不成立。

---

## 十三、推荐的下一步

建议按如下顺序继续推进：

1. 固化目标交易所和单一接口组合。
2. 先做软件金标准订单簿与策略回放器。
3. 定义内部固定长度市场数据和订单意图消息。
4. 优先实现 FPGA 订单簿与策略内核。
5. 再决定是否值得继续做 TCP/TLS/WebSocket 卸载。

如果后续要继续深化，本路线图最自然的下一份文档应该是：

- 《低时延策略在定点硬件中的表示方法》
